# らじれこ運用支援ツール 要件定義

> Status: Draft v3 / 最終更新: 2026-08-04
>
> 本番の実行形態は **トレイ常駐 per-user**([ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md) /
> [ADR-0013](adr/0013-velopack-per-user-updates.md))。Windows サービス・EventLog シグナル・named pipe を
> 前提にした記述は §3.1 / §7.1 / §7.2 のバナー下に**歴史として**残してある。

## 1. 背景・目的

ラジオ録音(らじれこ / 旧 radikool)で貯めた音声ファイルを、手作業で整理・配信するのは
手間がかかる。本ツールは以下を自動化・支援する。

1. **整理(正規化)**: 各録音ツールが出力する音声のメタデータを、Jellyfin 音楽ライブラリで
   扱いやすい規約へ正規化する。
2. **統合(取り込み)**: らじれこ・radikool など**複数ソース**を、単一の Jellyfin ライブラリ
   (NAS 上)へ束ねる。
3. **同期支援**: 整理済みファイルを NAS 上の Jellyfin ライブラリへ届け、スマホ(Jellyfin
   アプリ)から聴取できる状態にする。
4. **手動編集(UI)**: 取り込み後のタグ/ファイル名を、Windows デスクトップアプリで
   一括・個別に修正できる。

## 2. 用語

| 用語 | 意味 |
|------|------|
| らじれこ | 現行のラジオ録音アプリ。M4A(AAC)を `I:\radio\tmp` 系に出力 |
| radikool | 旧録音アプリ。過去分の音声を別の場所に保存(形式・命名は要調査 §5.2) |
| ソース / importer | 録音ツール別の入力。ツール毎にパーサ(importer)を差し替える |
| 配信先 / Z: | NAS 上の Jellyfin 音楽ライブラリ(`Z:` = `\\192.168.11.121\share`) |
| 台帳(ledger) | 取り込み済みを記録する冪等性用の状態ストア(ローカルディスク) |
| 正規名 | 表記ゆれを吸収した番組の正式表示名(alias 設定で管理) |
| 案A | 「1 番組 = 1 アルバム(全回集約)」の Jellyfin マッピング方針 |
| import-once | パイプラインは各ソースを 1 回だけ取り込み、取込後の Z: は触らない原則(§8) |
| 取込要約シグナル | 新規取込が発生したとき常駐が生成する要約(1 走査 = 最大 1 件に集約。提示とは独立、§7.1) |
| 取込通知 | 取込要約シグナル/取込失敗シグナルを受けてデスクトップへ提示する通知(§7.1) |
| 制御チャネル | 利用者 → 常駐へ指示を出す経路。ローカル同一ユーザー限定(§7.2) |

> 通知・制御レイヤの語彙(取込要約シグナル / 取込通知 / 制御チャネル / 制御コマンド)の**権威定義は
> リポジトリ root の [`CONTEXT.md`](../CONTEXT.md)** に置く。本表は §7.1/§7.2 が使う最小限のみ再掲する。

## 3. 環境・トポロジー

ツールは **Windows 上でネイティブ実行**する。録音元(I: ローカル HDD / radikool 保存先)も
配信先(Z: NAS)も Windows からネイティブに見えるため、WSL の `/mnt` 制約を回避する。

```
[同一PC Windows側]
    らじれこ  → I:\radio\tmp\... (M4A・ローカルHDD)   ┐
    radikool → 別の保存先(MP3・§5.2 要調査)         ├─ ソース(読取専用で参照)
                                                       ┘
        │  ① 自動パイプライン(FileSystemWatcher監視 or 全走査)+ サイズ安定判定
        │     → パース → 正規化 → import-once で Z: へ非破壊コピー & タグ付与
        ▼
[別マシン / NAS]  Jellyfin 音楽ライブラリ(Z: = \\192.168.11.121\share)
        ▲  ② 取込後の編集はデスクトップアプリが担当(タグ/ファイル名)
        │     [Windows デスクトップ編集アプリ] ── TagLib# で Z: を直接読み書き
        │  ③ スキャン / メタデータ・リフレッシュ(Jellyfin API)
        ▼
    Jellyfin 配信 → スマホ(Jellyfin アプリ)

    台帳(ledger, SQLite) … ローカルディスク(C: 等)。Z:/SMB には置かない
```

### 環境由来の制約・前提(重要)

- **実行ホストは Windows**(C#/.NET)。らじれこ RADIO=`I:\radio\tmp\...`(ローカル HDD)、
  配信先=NAS 共有。ソース監視(I:)とタグ操作(TagLib#)はネイティブ。
- **Windows 実行なので inotify 制約はない** → ファイル監視(FileSystemWatcher)が使える。
  ただし**らじれこ書き込み中の掴み防止のためサイズ安定判定は必須**。ポーリングも代替可。
- **録音元はローカル、Jellyfin は別 NAS** → 配信には**転送が必須**。処理は「原本読取専用 +
  NAS 上のコピーにタグ付与(非破壊)」。
- **★ NAS へは UNC(`\\192.168.11.121\share`)でアクセスする。ドライブレター `Z:` は使わない。**
  当初の理由は「マップ済みネットワークドライブはユーザー単位で、**Windows サービスのサービスアカウント
  からは見えない**」ことだった。[ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md) の
  トレイ常駐 per-user 移行で常駐がユーザーとして動くようになり、**この制約自体は消滅**した
  (資格情報のダンスも不要)。それでも **config は UNC を正**とする — ドライブレターの割り当ては
  環境依存で、設定を機械間で持ち回れなくなるため。
- **状態ストア(台帳・SQLite 等)はローカルディスクに置く**。SMB(NAS)上の SQLite は破損する。
- **WSL からは NAS のマップ済みドライブが見えない**ため実行ホストは Windows。開発/ビルドも
  Windows(.NET SDK)で行う(§11)。

### 3.1 実行形態(旧:単一 exe = 常駐サービス + 単発 CLI)

> **⚠ [ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md) で置き換わった**(移行完了・
> エピック #62、2026-07-19)。本番の常駐は **Windows サービス → トレイ常駐**(ユーザーセッション
> 自動起動・非 admin per-user)になり、取り込みワーカーは `Radirec.Gui` に畳まれ、`radirec.exe` は
> dev/batch 単発 CLI 専用に縮小した。UNC 資格情報・EventLog・named pipe・`%ProgramData%` 配置の前提は
> すべて退役(データは `%LOCALAPPDATA%\RadirecData`。[ADR-0013](adr/0013-velopack-per-user-updates.md))。
> **以下は移行前の設計**で、当時の記録として残す。現行の構成は §10 / §11 を参照。

本番形態は **単一 exe `radirec.exe`**。同一の取り込みエンジン(`Radirec.Core`)を、常駐サービスと
単発 CLI の 2 通りで動かす。両者は 1 つの実行体に **verb** で統合し、配布物を 1 本化して Core
バージョン不一致事故を構造的に防ぐ([ADR-0005](adr/0005-single-exe-cli-service-merge.md))。
実行体とデータは分離配置する(実行体 = `C:\Program Files\radirec\`、データ = `%ProgramData%\radirec\`。
[ADR-0006](adr/0006-binary-data-separation-and-path-resolution.md))。

- **`radirec.exe service`(常時監視・本番)**: I: を FileSystemWatcher 監視し検知即取り込み。
  `Microsoft.Extensions.Hosting.WindowsServices` で Windows サービスとして自動起動・自動再起動。
  コンソールが無いためログはイベントログへ。
- **`radirec.exe ingest` / `refresh`(単発・開発・バッチ)**: `ingest --dry-run` / `ingest` /
  `refresh`。手動実行・開発検証・サービスを入れずの動作確認に使う。Task Scheduler での定期実行も可。
- **★ NAS は UNC(`\\192.168.11.121\share`)でアクセス。ドライブレター `Z:` は使わない。**
  理由: マップ済みネットワークドライブはユーザー単位で、**サービスアカウントからは不可視**。
  config は UNC を正とする(§3)。
- **サービスアカウント/資格情報**: NAS(UNC)へ書ける **自分の Windows アカウント**で実行する
  (`install.ps1` が `-Credential` で登録し、`SeServiceLogonRight` を付与。[ADR-0007](adr/0007-distribution-via-powershell-scripts.md))。
- 台帳(SQLite)はサービスと CLI から同時アクセスされうる → **WAL 等で並行アクセスを許容**。

### 3.2 らじれこ自動スリープとの連携(★重要な運用前提)

らじれこは**録音終了後に自動スリープ**する設定があり、録音後 ~30 秒で Windows がスリープしうる。
常駐監視で「スリープ前に処理を挟む」狙いは妥当だが、**30 秒に賭けるのは脆い**(長尺番組は
NAS 転送が 30 秒を超えうる/コピー中に割り込まれる)。**らじれこは強制スリープ(能動的にスリープさせる)
であることをユーザーに確認済み** → `SetThreadExecutionState` は効かないので**採用しない**。
「30 秒以内に処理」を必須要件にはせず、**キャッチアップ + 冪等 + 中断耐性で"取りこぼさない"を保証**する
([ADR-0003](adr/0003-catchup-over-sleep-race.md)):

1. **復帰/起動時/定期フルスキャン(キャッチアップ)= 主機構**: 強制スリープ中は監視も止まり
   FileSystemWatcher はイベントを取りこぼす。**常駐の起動時・スリープ復帰時(電源イベント購読)・
   定期(安全網)に未処理をフルスキャン**して取り込む。import-once(§8)で冪等なので二重取り込みなし。
   → 30 秒に間に合わなくても次回復帰で確実に処理。
2. **リアルタイム検知(best-effort)**: 起きている間は `FileSystemWatcher` で検知即取り込み(デバウンス+
   安定判定)。強制スリープに邪魔されても①が回収する。
3. **中断耐性**: コピーはテンポラリ(`.partial`)→完了後リネーム、台帳は完了後記録。スリープでコピーが
   切れても半端ファイルを残さず、未記録として次回再取り込みされる。**常駐の起動時に孤児 `.partial` を掃除**。

→ ①+②+③ で、30 秒の成否・イベント取りこぼしに依存せず取りこぼしゼロを保証する。
`SetThreadExecutionState` は将来らじれこがアイドルスリープ運用に変われば最適化として再検討。

## 4. スコープ / 非スコープ

### スコープ
- 複数ソース(らじれこ / radikool)からの音声取り込み(importer 差し替え式)
- ファイル名・既存タグからのメタデータ抽出と Jellyfin(Music)向け正規化
- import-once での Z: への非破壊コピー & タグ付与(§8)
- Jellyfin ライブラリのメタデータ・リフレッシュ起動
- 番組正規名の alias 設定管理
- 取込後の一括正規化・一括タグ編集・実リネーム(**CLI で提供**、§10)
- **(保留)Windows デスクトップ編集アプリ**: 対話的な一覧編集。CLI 運用後に要否判断(§10.1)
- ドライラン・ログ・冪等な再実行

### 非スコープ
- らじれこ/radikool 自体の録音制御・スケジューリング
- 音声の再エンコード・トリミング・CM カット
- スマホへの直接ファイル同期(Jellyfin 配信で代替)
- Jellyfin サーバの構築・運用
- Jellyfin 標準メタデータエディタの再実装(差別化は §10 の一括/rename/alias 適用に置く)

## 5. 入力仕様(ソース別)

### 5.1 らじれこ(観測済み)

**ディレクトリ**
```
{RADIOルート}/{放送局}/{番組名を空白除去した英数字フォルダ}/{ファイル}.m4a
例) .../J-WAVE/LOGISTEEDRADIONOMICS/[J-WAVE]LOGISTEED RADIONOMICS(TimeFree)_20260612223000.m4a
```

**ファイル名文法(最も信頼できる抽出元)**
```
[{放送局}]{番組名}(TimeFree)_{YYYYMMDDHHMMSS}.m4a
 └放送局   └番組名(空白あり) └録音種別  └放送開始日時(JST)
```

**既存の埋め込みタグ**
| タグ | 実例 | 扱い |
|------|------|------|
| `title` | `LOGISTEED RADIONOMICS 20260612` | 冗長。上書き |
| `artist` | `鶴崎仁香（日向坂46）` | **出演者**。回ごと変動。維持(全角括弧に注意) |
| `album` | `J-WAVE` | **放送局**。Music では粗い。上書き |
| codec | aac 48kb/s / 約30分 / mp4a | 変更しない |

**観測された表記ゆれ**: 同一番組で `SONYSONPO QUEST` → `SONY SONPO QUEST`(2025-05 末)。
フォルダ名 `SONYSONPOQUESTFORTHEFUTURE`(空白除去)は空白ゆれには安定。→ 手動マージ可能な
alias 設計が必要(§9)。

**ファイル名の 3 形状(実データ 2176 件で検証)**:
唯一の普遍アンカーは末尾 `_{YYYYMMDDHHMMSS}.m4a`。これを起点に解析する。
- A `[局]番組(TimeFree)_ts`(2077 件): 標準。
- B `[局]番組_ts`(56 件): 録音種別マーカー無し。マーカーは既知許可リストの末尾一致のみ剥がす。
- C `番組_ts`(43 件): `[局]` プレフィックス無し。局はフォルダ名を権威にする。

**ファイル名から採るのは 放送局(`[..]`)・録音種別マーカー・放送日時 のみ**。
**番組の同一性(アルバム)はフォルダ名を拠り所にする**([ADR-0001](adr/0001-program-identity-anchored-to-folder.md))。
らじれこはファイル名の頭に週替わりゲスト名を入れる(例 `Awesome City Clubのオールナイトニッポン0(ZERO)`)ため、
ファイル名由来の番組名は回ごとに変動する。フォルダは安定なので、それを番組の識別に使う。ゲストは各回の
`artist`(元タグ由来)に残る。ラテン番組のフォルダ名(空白除去形)を整えたい場合は `programs.json` の
`Canonical.Album` で表示名を指定する(§9)。ジャンク録音は config のスキップパターンで除外。

### 5.2 radikool(観測済み / MP3・ID3)

**フォーマット**: MP3。タグは ID3。**らじれこと構造が大きく異なる**ため importer は別実装。

**ディレクトリ**
```
{radikoolルート}/{放送局コード}/{番組名}_{YYYYMMDD}.mp3
例) I:\d\radikool\records\LFR\オードリーのオールナイトニッポン_20200823.mp3
```
- 放送局フォルダは **radiko の局 ID コード**(`LFR` = ニッポン放送 等)。
- ファイル名 = **番組名 + 放送日(YYYYMMDD、時刻なし)**。

**既存の ID3 タグ(観測値)**
| フレーム/タグ | 実例 | 意味 | 抽出時の扱い |
|------|------|------|------|
| `title` (TIT2) | `オードリーのオールナイトニッポン` | 番組名 | §6 で放送日に上書き |
| `artist` (TPE1) | `オードリー(若林正恭/春日俊彰)` | 出演者(**半角括弧**) | 維持(括弧種は正規化検討) |
| `album` (TALB) | `オードリーのオールナイトニッポン` | 番組名(既にアルバム=番組) | 正規名へ |
| `genre` (TCON) | `ニッポン放送` | **放送局の表示名** | **ここから放送局を抽出**した後、`ラジオ` に上書き |
| `comment` (**TXXX**:comment) | `2020年08月23日` | 放送日(和文)。旧 Lavf は標準 COMM ではなく **TXXX** で書く | 案A で除去(空にする) |

**らじれことの差分(設計に反映)**
- **放送局が 2 系統**: フォルダ=局 ID コード `LFR` / genre=表示名 `ニッポン放送`。らじれこは
  フォルダ=表示名(しかも `J-WAVE` は英語・`ニッポン放送` は和文と揺れる)。→ **放送局マスタ**
  (局 ID コード・表記ゆれ → 正規表示名)を alias とは別に持つ(§9)。
- **放送日時が日付のみ**(時刻欠落)→ §8 同一性キーは時刻欠落を許容する。
- **抽出順序**: 放送局を genre から取り出す処理は、genre を `ラジオ` に上書きする**前**に行う。

**実装検証で判明(M4-A・実データ 70 件)**
- **局は genre タグが権威。局コードフォルダは信用しない**: `fm_tokyo` フォルダに genre=`NHK FM(東京)`
  のファイルが実在(radikool の誤分類)。→ 局は genre から解決し、フォルダ局コードは genre 欠落時のみの
  フォールバックにする([ADR-0004] 参照 / [CONTEXT.md])。
- **genre 自体も表記ゆれ**: `NHK-FM（東京）`(全角)と `NHK FM(東京)`(半角・ハイフンなし)が同一局。
  NFKC でも畳めないため両表記を stations.json の alias に登録する。
- **comment は TXXX** で書かれており、汎用 `Comment` の空代入では消えない → TXXX/COMM を明示除去する。
- **同日重複マーカー `(N)`**: 中身の違う同日別録音を、重複マーカーの番号で区別して両方取り込む([ADR-0004])。

## 6. 正規化仕様(Jellyfin Music タグ・マッピング / 案A)

| タグ | セット値 | 例 | 根拠 |
|------|---------|----|----|
| `albumartist` | 放送局 | `J-WAVE` | Album Artists で「局 → 番組」と辿れる安定グルーピングキー |
| `album` | 番組の正規名 | `LOGISTEED RADIONOMICS` | 1 番組 = 1 アルバム(案A) |
| `artist` | 出演者(原タグ維持) | `鶴崎仁香（日向坂46）` | 情報量保持。グルーピングは albumartist で担保 |
| `title` | 放送日(パートは `(N)` 付き) | `2026-06-12` / `2026-06-12 (1)` | アルバム内で回一覧が日付表示 |
| `date` | 放送日(ISO) | `2026-06-12` | — |
| `disc` (`disk`) | 放送年 | `2026` | 年でディスク分割 |
| `track` (`trkn`) | MMDD(数値)。統合番組の回は `MMDD*10+パート` | `612` / `1011` | 年内を日付順ソート、同日はパート順 |
| `genre` | `ラジオ` | | フィルタ用 |
| `comment` | 録音種別/由来 | `TimeFree` / `radikool` | 出所を保持 |

### 設計上の注意
- **MP4 の `trkn`/`disk` は 16bit 整数(≤65535)**。`disc=年`・`track=MMDD(≤1231)` は収まる。
  「`track=YYYYMMDD` に統合」は**オーバーフローするため禁止**。年と MMDD 分離はこの制約が理由。
  統合番組の回は `track=MMDD*10+パート`(≤ 12319、パートは 1〜9 想定)で細分化しソート順を確定。
- `track` は数値ソートされるため 0 埋め不要。0 埋めが要るのはファイル名・タイトル等**文字列**の場合のみ。
- **パート**: 統合番組(ふらっと(1)/(2) 等)の回は、ファイル名 `-N`・`track=MMDD*10+N`・
  `title` の `(N)` で区別され、アルバム内で part1→part2 の順に並ぶ([ADR-0002](adr/0002-same-day-tiebreak-by-time.md))。
  N は由来フォルダの `Folders` 順(1 始まり)で、放送日の重なりと関係なく付く(片方のパートしかない日も `-1` 等)。
  radikool の**重複マーカー** `(N)` 付き録音も、同じ `-N` / `(N)` / `MMDD*10+N` の形で出力される([ADR-0004](adr/0004-part-index-dedup-for-timeless-sources.md))。
- **Music を選んだ帰結**: レジューム再生位置は保持されない。30 分番組で「途中再開」要求が出たら再検討。
- radikool 由来で MP3 なら ID3 タグへ同等マッピング(TALB/TPE2/TPE1/TIT2/TDRC/TRCK/TPOS)。

## 7. 自動パイプライン(取り込み)

走査は①録音検知(FileSystemWatcher)②スリープ復帰 ③常駐トレイの起動時 ④定期(安全網)⑤**手動**
(制御チャネルの rescan、§7.2)のいずれかで起動する。以下は 1 走査分の処理:

1. **検知**: ソースルート配下の音声を FileSystemWatcher で検知、または起動時に全走査。ポーリング代替可。
2. **安定判定**: 書き込み中の掴み防止。サイズ(と mtime)が一定時間変化しないものだけ対象。
   `.part` 等の一時ファイルは除外。
3. **同一性判定**: §8 の同一性キー(放送局 / 番組 / 放送日時)を算出。**台帳に在れば取込済みとして
   スキップ**(import-once)。
4. **抽出**: ソース別 importer でパース(らじれこ=ファイル名文法優先 / radikool=別ロジック)。
5. **正規化解決**: alias 設定で番組の正規名・追加タグを解決。未知番組はソースの番組名を
   フォールバックにし、警告ログで alias 追記を促す。
6. **非破壊コピー**: 原本(読取専用)を `Z:\` の Jellyfin ライブラリへコピー。配置は
   `{放送局}/{正規番組名}/...`(Jellyfin は主にタグ参照。人間可読性のため)。テンポラリ →
   完了後リネームで不完全ファイルを残さない。
7. **タグ付与**: コピー先に §6 のタグを書き込む(TagLib#)。
8. **台帳記録**: 同一性キーを取込済みとして記録(§8)。
9. **リフレッシュ**: Jellyfin API でメタデータ更新を起動。
10. **要約シグナル発行**: その走査で**新規取込があった場合のみ**、取込結果を番組(アルバム)単位に
    まとめた取込要約シグナルを発行する(取込済スキップのみの走査では発行しない、§7.1)。

### 7.1 取込通知(サービス→デスクトップ)

> **⚠ [ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md) で機構が変わった**: トレイ常駐移行で
> **EventLog シグナル(EventID 1001/1002)は退役**し、取り込みワーカーをトレイが内包するため通知は
> **in-process で直接トースト**する(publisher/subscriber の 2 ツリー分割は不要に)。以下の「サービス発の
> シグナル + 受け手 GUI」記述は移行前の設計。ドメイン概念(1 走査=最大 1 要約に集約)は不変。

取り込みが自動で進むと、利用者は「何がいつ入ったか」に気づけない。そこで **1 走査で新規取込が
起きたとき、常駐サービスが取込要約シグナルを 1 件発行**し、ユーザーセッションの常駐 GUI が
デスクトップ通知(トースト)として表示する。

- **契約(振る舞い)**: 1 走査につきシグナル最大 1 件で、その走査で取り込んだ放送回を番組単位に
  集約する(起動時キャッチアップの大量取込もスパムにせず 1 件に束ねる)。**発行者はサービス側**で、
  受け手 GUI の生死に依存しない(サービスは通知の有無に関わらず取込を完遂する)。
  → #127 で、その走査で**初めて取り込んだ番組フォルダ**のうち、統合設定が無く**兄弟フォルダ**
  ([CONTEXT.md](../CONTEXT.md))のあるものも同じシグナルに載せて運ぶようにした(別シグナルにはしない)。
  取込通知はそれを本文の 1 行として示し、全件は `gui.log` に書く(`docs/usage.md` §6)。
  → #155([ADR-0018](adr/0018-attention-items-derived-from-state.md))で、兄弟フォルダの知らせを取込要約シグナルと
  取込通知から外し、管理画面の要対応(§10.3)に移した。取り込みの走査は兄弟フォルダを調べなくなった(要対応が台帳から
  毎回計算するので、走査での検出と `gui.log` への記録は重複になるため)。
- **表示の制約**: サービス(Session 0)はデスクトップに通知を出せないため、**表示はユーザー
  セッションの常駐 GUI(`Radirec.Gui`)**が担う。
- **不在中サマリ**: 受け手が停止していた間に発行されたシグナルは、次回起動時に **1 件の通知へ
  集約**して提示する(不在中サマリ、[CONTEXT.md](../CONTEXT.md) が語彙の権威)。購読位置(EventLog
  bookmark)を永続化して不在期間を再構成する。再構成が信頼できないとき(初回起動・記録が失効/
  破損)は提示せず現在以降のみ購読する(縮退)。過去分を個別トーストで再生はしない(ログオン時の
  大量トースト回避。ADR-0009)。取込自体は受け手の生死に依存せず完了・記録される。
- **取込失敗の通知**: 1 走査で**ファイル単位の失敗**(パース失敗・書込/タグ/台帳失敗)が起きたとき、
  サービスは成功要約(1001)とは**別の取込失敗シグナル(EventID 1002)**を発行し、受け手が失敗通知
  (トースト)として表示する。同じ失敗を毎走査で鳴らさないよう**発行側で de-dup**(新しく現れた失敗
  だけ発行・成功で解除・再起動を跨いで永続)。失敗も不在中サマリに参加する(de-dup 済みゆえ catch-up
  しないと見逃す)。**反映失敗**(Jellyfin 更新の失敗)は取込失敗とは別物で対象外(将来別シグナル)。
  シグナルの分割・de-dup・catch-up 参加の判断は [ADR-0011](adr/0011-ingest-failure-as-separate-eventlog-signal.md)。
- 発行機構(EventLog を跨プロセス片方向バスに使う判断)は [ADR-0008](adr/0008-ingest-notification-via-eventlog-signal.md)、
  受け手 GUI(非パッケージ WPF トレイ + 従来トースト、`Radirec.Gui`)は
  [ADR-0009](adr/0009-toast-receiver-unpackaged-wpf-tray.md) に委ねる。`Radirec.Gui` は M5 デスクトップ
  編集アプリ(§10.1・保留)の最初の tracer slice で、現状は**表示専用**、編集本体は後載せ。

### 7.2 制御チャネル(利用者→サービス)

> **⚠ [ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md) で機構が変わった**: トレイ常駐移行で
> **named pipe 制御チャネルは退役**し、rescan/reload/status は**トレイメニューからの in-process 呼び出し**に
> なった(CLI 制御 verb は廃止。移設先は**トレイメニュー**で、下の「現在地」を参照)。以下の named pipe 記述は
> 移行前の設計。「利用者→常駐へ指示を出す」概念(3 コマンド)は不変。
> → #126 で 4 種目の「再適用の実行」を足した(下の一覧)。

取込通知が**サービス発・一方向**なのに対し、常駐サービスへ**利用者側から指示を出す**逆方向の
経路を制御チャネルとして持つ。到達範囲は**ローカル同一ユーザー**に限定し、リモート制御は含めない。

現時点の制御コマンドは 4 種([CONTEXT.md](../CONTEXT.md) が語彙の権威):

- **rescan(手動再スキャン)**: 自動トリガを待たず取り込み走査を今すぐ 1 回要求する(受理まで。
  完了は待たない)。§7 の走査トリガ⑤に相当。
- **reload(設定リロード)**: `radirec.json` の変更をサービスに反映させる。**反映はサービス実質
  再起動相当**で部分反映はしない(config 由来ランタイムを丸ごと再構築)。不正 config は受理時に
  弾かれ、再構築に失敗しても**旧構成のまま稼働継続**する。
- **status(状態取得)**: サービスの**ライブ状態**(稼働状態・監視ルート・最終スキャン完了時刻と
  その結果)を読む。
- **再適用の実行**(#126 で追加。常駐からのみ): 統合設定の**再適用**
  ([ADR-0016](adr/0016-reapply-program-settings-to-ingested-episodes.md))の dry-run の結果を返し、
  利用者が確認したら実行する。rescan / reload と違い、受理ではなく**結果が返るまで待つ**。確かめる設定は 2 通り:
  設定リロードを反映した保存済みの設定と、管理画面の番組ページで編集した**保存前の設定**(#154。確かめるときは
  リロードしない)。保存前の設定で確かめたものは、保存してから**設定リロード → 実行**を 1 つの続きとして行い、
  間に取り込みの走査を挟まない(リロードに失敗したら実行しない)。確認の後に設定・状態が変わっていれば(読み直した
  設定を確認のときと値で比べる)実行しない。

サービス未起動/未応答時は各コマンドともエラー表示 + 終了コード 1 で破綻しない。実装(named pipe・
同一ユーザー限定の認可・再構築のセマンティクス)は [ADR-0010](adr/0010-gui-service-control-via-named-pipe.md)、
Windows 実機での検証手順は [control-channel-verification.md](control-channel-verification.md) に委ねる。
利用者向けのコマンド一覧は [usage.md](usage.md) を参照。

**現在地**(バナーの外・移行後): 制御の窓口は**常駐トレイのメニュー**で、4 コマンドとも in-process 呼び出し
([ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md))。CLI の制御 verb
(`status`/`rescan`/`reload`)は廃止された。**手動再スキャンの移設先はトレイメニューの「今すぐ再スキャン」**で
(`ControlTrayMenu` → `IServiceControl.RequestRescan`)、常駐プロセス内の走査要求になる。
`radirec ingest` は移行前から在る **dev/batch 用の単発 CLI** で、常駐とは別プロセス — 制御コマンドの
移設先ではない(単発で走査したいときの手段としては使える)。状態はメニューを開いた時点のスナップショットとして
表示する。設定リロードと再適用の窓口は、トレイのメニューから管理画面(§10.3)へ移った(番組ページ。#154)。
トレイと管理画面からの操作は [usage.md](usage.md) §6 を参照。

## 8. import-once と冪等性(★中核設計)

**Z: への書き手は 2 つある**(自動パイプライン / デスクトップ編集アプリ)。両者が競合して
手修正を消さないよう、権限を明確に分離する。

- **パイプラインは import-once**: 各ソース音声を**同一性キー = (正規放送局, 正規番組名, 放送日
  [+時刻があれば])**で一意化し、**台帳に無いものだけを 1 回取り込む**。**取り込み済みの Z: ファイル
  には二度と触れない**(ソースの mtime が変わって再ダウンロードされても、同一性キーが既存なら
  再取込しない)。
  - 放送局・番組名は**正規化後の値**でキー化する(§9)。これにより radikool(コード `LFR`)と
    らじれこ(表示名)で表現が違っても同一放送局として一致し、**ソース跨ぎの重複取込を防ぐ**。
  - アルバムのグルーピングキーは日単位だが、**dedup(冪等判定)は放送時刻も見る**
    ([ADR-0002](adr/0002-same-day-tiebreak-by-time.md))。同一 `(局,番組,日)` でも**時刻が異なれば
    別放送**として両方取り込む(例: 時間帯分割番組 `ふらっと(1)/(2)`)。同時刻の再ダウンロードは冪等スキップ。
  - radikool は放送日のみ(時刻なし)。時刻なしは **`''`(時刻不明)として厳密一致**で扱い、同日の別録音は
    **part_index** で区別する(旧「同日どの時刻とも一致するワイルドカード」は #11 /
    [ADR-0004](adr/0004-part-index-dedup-for-timeless-sources.md) で撤去)。本物の 00:00 とは別値。
  - **内容ゲート**: 上記の同一性キー / ソースパスに加えて、**内容フィンガープリント(サイズ + 最終更新)
    + 放送日時**でも取込済み判定する([ADR-0014](adr/0014-content-fingerprint-import-dedup.md))。**ソースの
    番組フォルダをリネーム**したり**台帳を失った**りしてキー/パスが変わっても、内容が同じ回は再取込しない
    (無音の重複ファイル生成を防ぐ)。放送日時で裏取りするので、内容の違う同日別放送は取りこぼさない。
- **取込後の Z: は編集アプリが唯一の書き手**。手修正したタグ/ファイル名はパイプライン再実行で
  上書きされない。
  → 2026-09-24: 統合設定の再適用([ADR-0016](adr/0016-reapply-program-settings-to-ingested-episodes.md))も、
  利用者が明示的に実行したときだけ Z: の出力ファイルを動かし、`album` / `title` / `track` を書き換える
  (他のタグは残す)。自動パイプラインが取込後の Z: を書き換えないことは変わらない。
- **台帳(ledger)**: ローカルディスク(C: 等)の SQLite。記録内容 = 同一性キー / ソースパス /
  取込日時 / 出力先パス / 正規化ルール版 / 内容フィンガープリント。**Z:(SMB)には置かない**(破損回避)。
- ドライラン(`--dry-run`)で「何をどこへ取り込むか」を副作用なしに提示。
- 例外的に「正規化ルールを一括再適用したい」場合は、編集アプリ側の明示操作として提供する
  (自動パイプラインは再正規化しない)。
  → 2026-09-24: 再適用([ADR-0016](adr/0016-reapply-program-settings-to-ingested-episodes.md))は
  CLI(`radirec reapply`)とトレイ(#126)の明示操作として提供し、Z: の出力ファイルも動かす。

## 9. 設定ファイル(放送局マスタ / 番組 alias / config)

複数ソースで放送局・番組名の表現が揺れるため、2 段の正規化辞書を持つ。

### 9.1 放送局マスタ(stations.yml)
局 ID コード(radikool の `LFR` 等)・表記ゆれ(らじれこの `J-WAVE`/和文名)を**正規表示名**へ寄せる。

**自動シード可能**: radikool は各ファイルの `genre` に局表示名を持つ(例 `LFR` フォルダ → genre
`ニッポン放送`)。importer が各局フォルダの 1 ファイルを読めば「コード → 表示名」を自動生成できる。
手動 config は差分・らじれこ側の英語表記統合(`TOKYOFM`→`TOKYO FM` 等)に限定する。

**radikool 観測済み局フォルダ**: `FMT` / `JOAK-FM` / `LFR` / `QRR` / `fm_tokyo`。
※ `FMT` と `fm_tokyo` は**同一局(TOKYO FM)の可能性が高い**(radikool 内でも表記割れ)。
  genre 実値で確認のうえマスタで正規名へ統合する。
```yaml
# stations.yml(例。radikool genre からの自動シード + 手動補正)
stations:
  - canonical: "ニッポン放送"
    aliases: ["LFR", "ニッポン放送"]
  - canonical: "文化放送"
    aliases: ["QRR", "文化放送"]
  - canonical: "TOKYO FM"
    aliases: ["FMT", "fm_tokyo", "TOKYOFM", "TOKYO FM"]
  - canonical: "NHK-FM"
    aliases: ["JOAK-FM"]
  - canonical: "J-WAVE"
    aliases: ["J-WAVE"]
```

### 9.2 番組 alias(programs.json)
番組の同一性はフォルダ名([ADR-0001](adr/0001-program-identity-anchored-to-folder.md))。
**フォルダ名**(`Folders`)から表示アルバム名(`Canonical.Album`)を引く。複数フォルダ →
1 アルバムの**手動マージ**も可(照合キーは空白除去・大文字化で吸収)。
```jsonc
{
  "Defaults": { "Genre": "ラジオ" },
  "Programs": [
    { "Match": { "Station": "J-WAVE", "Folders": ["LOGISTEEDRADIONOMICS"] },
      "Canonical": { "Album": "LOGISTEED RADIONOMICS" } },
    { "Match": { "Station": "TBSラジオ", "Folders": ["パンサー向井のふらっと(1)", "パンサー向井のふらっと(2)"] },
      "Canonical": { "Album": "パンサー向井のふらっと" } }
  ]
}
```
`albumartist` は放送局マスタで解決した正規局名を使う(番組 alias に重複記載しない)。
未登録のフォルダはフォルダ名がそのままアルバム名になる(設定不要)。

メモはエントリごとの `Note`、分けておく兄弟フォルダは最上位の `KeepSeparate`(1 件 =
`{ "Match": { "Station", "Folders" }, "Note" }`)に持つ([ADR-0017](adr/0017-management-window-owns-programs-json.md))。
どちらも取り込みと再適用の解決には使わない(`KeepSeparate` を読むのは、要対応と再適用の確認に出す「統合設定の無い
兄弟フォルダ」の計算だけ。[ADR-0018](adr/0018-attention-items-derived-from-state.md))。

> **書き手の現状(#153)**:全体を書き直す書き手(`ProgramsFileWriter`)は Hosting にある。書く前に
> `programs.json.bak-YYYYMMDD-HHmmss` を作り、一時ファイル経由で置き換え、読み込んだときから中身が変わっていたら書かない。
> コメントは残らないので、コメントの件数を数えて初回保存の確認に使えるようにしてある。`Note` が null のエントリ・空の
> `KeepSeparate` はキーごと書かない(使わない限り古い版でも読める)。これを呼ぶのは、管理画面の番組ページ(§10.3・#154)と
> 要対応の「分けておく」(#155。コメントがあるときはその場で書かず、番組ページの下書きへ回す)。兄弟フォルダの提案の追記
> (#148 の `ProgramsFileAppender`)は #155 で退役した(要対応の「統合する」が番組ページの下書きを作る)。

### 9.3 環境設定(config)
らじれこ RADIO ルート、radikool ルート、配信先ルート=`Z:\...`、Jellyfin API URL/トークン、
監視/ポーリング間隔、安定判定の待機秒数、台帳パス(ローカルディスク)を持つ。

## 10. アプリケーション構成(レイヤ分離)

性質の違う 2 責務(機械的な**取り込み** / 人手の**キュレーション**)を、**1 コア + 薄い
フロントエンド**に分離する。単一リポジトリ・レイヤ分離とし、GUI は後回しの独立フロントエンド。

```
radirec-tool/
  core/   # ドメインロジック: パース(importer) / 正規化ルール / 放送局・番組解決 /
          #   タグ書込(TagLib#) / import-once 台帳 / Jellyfin リフレッシュ。GUI 非依存・テスト可能
  cli/    # 薄い入口(dev/batch の単発)。radirec ingest / reapply / refresh / history
  gui/    # 本番の常駐本体。取り込みワーカー + トレイ + 取込通知 + 管理画面(取込履歴を含む。§10.3)+ 制御 + 自己更新。
          #   取込後編集グリッド(§10.1)は同プロジェクトに後載せ・保留
  docs/  tests/
```

> **常駐は gui 側**([ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md))。当初は
> cli に `service` verb を持たせて Windows サービスとして常駐させたが、トレイ常駐 per-user へ移行し、
> ワーカーは gui に畳まれた。制御チャネルの窓口も cli からトレイメニューへ移っている。

- **原則**: ドメインロジックは全て `core/` に置き、CLI/GUI は薄いアダプタ。
- **CLI で提供する編集操作**(GUI 前でも運用可能。**いずれも M4 / #4 のスコープで未実装** —
  現行のコマンドは `ingest` / `reapply` / `refresh` / `history` の 4 つ):
  → **#4 は not planned で閉じた(2026-09-25・[ADR-0020](adr/0020-cli-as-agent-front-via-control-channel.md))**。
  下の 2 つは作らない。統合と正規名の揃え直しは再適用(`reapply`。ADR-0016)と管理画面が引き取った。
  - **一括正規化**: alias/放送局マスタ更新 → 該当アルバム全回へ再適用(`radirec apply-alias`)。
  - **一括タグ編集 / 実リネーム**: 番組(アルバム)単位でタグ修正・Z: 上ファイル名の規約統一。
- **個別のタグ微修正**は当面 **Jellyfin 標準メタデータエディタ**で代替可能。

### 10.1 デスクトップ編集アプリ(gui / 編集本体は後回し・任意)

`Radirec.Gui` プロジェクト自体は**取込通知の受け手(トレイ)として出荷済み**(§7.1・ADR-0009)。
以下の**編集本体**は同プロジェクトへの後載せで、CLI 運用で不足が判明したら着手する。差別化は
「一覧グリッドでの対話編集」。実装可否は運用後に判断。GUI(トレイ + 編集)の将来オプションの俯瞰は
[roadmap.md](roadmap.md) を参照。番組の設定の編集と取り込みの状況を扱う**管理画面**は編集本体とは別物で、
§10.3 で先に作る(このゲートとは関係しない)。

> **注**: [ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md) の常駐移行が
> **2 ツリー統合(C2 の構造前提)を先に確立済み**。`Gui → Core` の直接参照が入ったわけではなく、
> Core の型が推移参照(`Gui → Hosting → Core` / `Gui → Gui.Core → {Core, Hosting}`)で `Radirec.Gui` の
> コンパイル面に乗っている状態(§11 の参照グラフ)。よって編集本体着手時は構造前提が既に整っており、
> 残るは編集機能そのもの。ただし**「CLI 運用で不足が判明したら着手」のゲート自体は維持**
> (移行は常駐単純化が動機で、編集本体の greenlight ではない)。

- **一覧編集 UI**: アルバム/回のグリッドで title/artist/album/albumartist/disc/track 等を直接編集。
- 編集後は Jellyfin API リフレッシュを起動。台帳・alias とは競合しない(編集側が Z: の権威、§8)。
- **ファイル名編集の位置づけ(要確認)**: Jellyfin Music はタグ表示が主で、**リネームは Jellyfin
  上の見た目を変えない**(§12)。実ファイル閲覧・別プレーヤ利用等が目的なら実装、そうでなければ後回し。

### 10.2 汎用コア / 個人拡張の境界(将来配布への布石)

配布プロダクト = **整理コアのみ**(らじれこ M4A の rename + タグ正規化)。個人固有の
Jellyfin/NAS 同期・radikool 移行は**疎結合な拡張**として隔離し、後から抽出できる形を保つ(§14)。

- **個人固有値はコードに書かず config**(I:/Z:/NAS IP/局マスタ等)。出荷デフォルトは安全値 + サンプル。
- **importer は差し替え式**: らじれこ importer = 汎用 / radikool importer = 個人拡張。
- **出力ターゲットを抽象化**(核となる分離線):
  - `LocalFolderTarget`(汎用): 整理済みをローカルの整頓フォルダへ出力。一般ユーザー向け。
  - `JellyfinLibraryTarget`(個人拡張): Z: へコピー + Jellyfin リフレッシュ。
- これにより「らじれこ整理」だけを取り出して配布でき、自分は拡張(radikool importer /
  Jellyfin ターゲット)を足して使う。**両者が同一コアを共有**。
- **GUI は配布フロントエンドと兼用**を意識(§10.1 の一覧編集を整理コアの上に載せる)。

### 10.3 管理画面(設計確定。エピック #159)

§10.1 の編集本体とは別に、**管理画面**(CONTEXT.md)を `Radirec.Gui` に足す。動機は、番組の設定(`programs.json`)を
エディタで直すのがつらいこと、取り込みの状況を 1 つの画面で見たいこと、トレイのメニューと通知が増えて煩雑になったこと
(2026-09-25 の設計。決定の一覧は issue #5 のコメント)。**回のタグを 1 つずつ直す機能は含めず、§10.1 のゲートは残す**。
将来、編集本体を作るときは管理画面のページとして載せる。

- **構成**:1 つのウィンドウに 5 ページ。同時に開けるのは 1 つだけで、閉じても常駐は続く。
  - **ホーム**:状態(稼働・最終スキャン)と「今すぐ再スキャン」/ **要対応** / **取込履歴**(新しい方の数件。「すべて表示」で取込履歴ページへ移る)
  - **取込履歴**:台帳の全件の一覧(列の見出しで並べ替え・出力先 / 取込元を開く・パスのコピー)。旧取込履歴ウィンドウ(#66)を引き継ぐ(#151 でウィンドウは退役)
    (全件をホームの中で広げると、要対応が押し出されるため分けた。#161)
  - **番組**:統合番組と分けておく兄弟フォルダの一覧・追加・編集・削除([ADR-0017](adr/0017-management-window-owns-programs-json.md))
  - **設定**:新規取込のトーストの切り替え / `radirec.json`・`stations.json` を読み取り専用で見せ、「ファイルを開く」と「再読み込み」を付ける。
    トーストの切り替えは管理画面用の設定ファイル `gui-settings.json` に持ち、`radirec.json` は書かない(#152・[ADR-0019](adr/0019-gui-settings-file-for-ingest-toast.md))
  - **バージョン情報**:版 / 今すぐ更新を確認 / 更新を適用して再起動
- **番組を保存する流れ**:編集 →「確認」で、**保存前の設定のまま**再適用の dry-run を行い、変更前→変更後を見せる →
  「保存して適用」(保存 → 設定リロード → 再適用)/「保存だけ」/「戻る」。「保存だけ」で食い違ったままの回は要対応に出る。
  `stations.json` を手で直した場合は、設定ページの「再読み込み」から同じ確認に進める。ファイルの変更の自動検知はしない。
- **要対応**:いまの状態から毎回導く([ADR-0018](adr/0018-attention-items-derived-from-state.md))。統合設定の無い兄弟フォルダの組
  (統合する / 分けておく)、解決していない取込失敗、番組の設定と食い違ったままの回。
- **トレイに残すもの**:版 / **Radirec を開く**(既定の項目。ダブルクリックでも開く)/ 今すぐ再スキャン / 状態・最終スキャン /
  更新を適用して再起動(保留中のみ)/ 再読み込みして再起動(縮退時のみ)/ 終了。ほかの項目は管理画面へ移し、トレイから消した:
  取込履歴(取込履歴ページ。#151)、設定リロードと設定ファイルのサブメニュー(設定ページ。#152)、再適用(番組ページ。#154)、
  今すぐ更新を確認(バージョン情報ページ。#157)。
- **通知**:取込失敗のトーストは常に出す。新規取込のトーストは設定ページで止められる(#152。以前の `radirec.json` の設定は
  失敗のトーストと失敗の記録も止めていたので分けた。旧設定は初期値としてだけ読む。[ADR-0019](adr/0019-gui-settings-file-for-ingest-toast.md))。
  兄弟フォルダの知らせはトーストから外して要対応へ移した(#155)。管理画面から操作したときの結果は、バルーンではなく画面の中に出す。
- **縮退時**(設定が読めない):管理画面は開けるが、設定を読めない理由と「ファイルを開く」「再読み込みして再起動」を出す。JSON のエディタは内蔵しない。
- **技術**:WPF + XAML + MVVM(CommunityToolkit.Mvvm)。ViewModel と計算は `Radirec.Gui.Core` / `Radirec.Hosting` に置いて
  WSL の CI でテストし、シェルは薄く保つ。見た目は HTML モックで詰めてから、RC タグを実機で確かめる。

## 11. 技術スタック・実行/開発環境

> 技術選定: **C#/.NET に確定**。理由 = 配布の最終形(非技術者向け Windows GUI / 単体 exe)に
> 最適で、Windows GUI・exe 配布・タグ操作(TagLib#)が一体で揃う。Python(mutagen)より
> コア初期開発速度は落ちるトレードオフを許容。


- 言語/ランタイム: **C# / .NET**(実行は Windows ネイティブ)
- **ソリューション構成**(レイヤ分離を .NET プロジェクトに対応、§10):
  - `Radirec.Core` — クラスライブラリ。ドメインロジック(importer / 正規化 / タグ書込 /
    import-once 台帳 / 出力ターゲット抽象 / Jellyfin 連携)。**クロスプラットフォームでテスト可能**。
  - `Radirec.Hosting` — 合成ルート + 環境設定・パス解決 + 制御(`Control/`)。**`Radirec.Cli` と
    `Radirec.Gui` の 2 フロントエンドが共有する合成層**なので Cli に畳まず独立を保つ([ADR-0012])。
  - `Radirec.Cli` — **単一 exe `radirec.exe`**(`Spectre.Console.Cli`)。**dev/batch の単発 CLI**
    (`ingest`/`reapply`/`refresh`/`history`)。TFM は `net10.0-windows`。中身は `Program.cs` だけの薄い入口で、コマンドは
    `Radirec.Cli.Core` にある(#178)。
    ※ かつては常駐サービス(`service` verb)と制御チャネル窓口(`status`/`rescan`/`reload`)も
    1 実行体に統合していた([ADR-0005])が、[ADR-0012] で常駐はトレイへ移り verb は廃止された。
  - `Radirec.Cli.Core` — `Radirec.Cli` のテスト可能な核(コマンド・`--json` の形・終了コード・`CommandApp` の設定。
    `Spectre.Console.Cli`)。TFM は `net10.0` で、Linux の CI でテストできる(#178・[ADR-0020](adr/0020-cli-as-agent-front-via-control-channel.md))。
  - `Radirec.Gui` — **本番の常駐本体**(独立 exe、WPF + WinForms、`net10.0-windows10.0.x`)。
    取り込みワーカー・取込通知・管理画面(取込履歴を含む。§10.3)・制御メニュー・自己更新を 1 プロセスで持つ([ADR-0012])。
    将来の配布フロントエンド兼編集 UI(M5)は同プロジェクトへ後載せ。`radirec.exe` とは実行モデルが
    別(ユーザーセッション GUI)なので別 exe。
  - `Radirec.Gui.Core` — `Radirec.Gui` のテスト可能ロジック(トースト文面整形・取込履歴行の整形・
    版表示・状態の文言)と、管理画面の ViewModel(§10.3。CommunityToolkit.Mvvm)。**CI で走らせられない
    WinRT/WPF/WinForms シェルから隔離**する置き場([ADR-0012])。
  - `Radirec.Tests` — 単体テスト(xUnit 等)。
  - **参照グラフ**: `Gui → {Gui.Core, Hosting}` / `Gui.Core → {Core, Hosting}` / `Cli → Cli.Core → {Hosting, Core}` /
    `Hosting → Core`。`Gui → Core` の直接参照は無く、Core の型は推移参照で乗る([ADR-0012])。
    `Gui.Core → Hosting` は管理画面の ViewModel が制御面(`IServiceControl` / `ServiceStatusSnapshot`)をそのまま
    受け取るための辺(#151。Gui.Core 側にインタフェースを切ると写しとアダプタを二重に保守することになるため)。
    詳細は [development.md](development.md) §プロジェクト構成 と [roadmap.md](roadmap.md) §前提。
- タグ操作: **TagLib#(TagLibSharp)**(MP4/M4A の track/disc/標準フィールド + MP3 ID3 の読み書き)。
  §6 は標準フィールドのみ使用(freeform 不要)。
- ファイル監視: **`FileSystemWatcher`**(Windows ネイティブ)。ポーリングは代替として併用可。
- 台帳: **SQLite(`Microsoft.Data.Sqlite`)**、ローカルディスク。Z:/SMB には置かない。
- Jellyfin 連携: REST API(`HttpClient`)。
- 設定: JSON/YAML(`appsettings.json` + 個別 config)。
- 配布: **Velopack の per-user インストーラ(Setup.exe)+ アプリ内自己更新**([ADR-0013](adr/0013-velopack-per-user-updates.md))。
  非 admin で入り、GitHub Releases をフィードに管理画面(バージョン情報)とトレイから更新する。GUI 枠組みは **WPF に確定**(ADR-0009)。
- **開発/実行環境**:
  - **開発・ビルド・実行は Windows**(.NET SDK / Visual Studio or `dotnet` CLI)。リポジトリは
    Windows 側(例 `C:\dev\radirec-tool`)に置く。WSL からは `/mnt/c/...` で編集可能。
  - `Radirec.Core`/`Hosting`/`Gui.Core`/`Tests` はクロスプラットフォーム(`net10.0`)で書き、
    WSL の linux `dotnet` でもビルド/テスト可能にする(パス依存は設定注入)。`Cli` / `Gui` は
    Windows 専用。取り込みワーカーが `SystemEvents.PowerModeChanged` に依存するため、
    ワーカーは Hosting ではなく `Gui` に置く(Hosting を Windows 専用にしないため。[ADR-0012])。

## 13. マイルストーン(コア+CLI → 常駐化 → 統合 → 通知・制御 → トレイ常駐移行 → 管理画面 → 編集 GUI は保留)

> M5(編集 GUI)本体の着手前に出荷済み(M6 の受け手トレイが M5 の最初の tracer slice を兼ねるため、
> 番号は M6 だが先行)。**M3 / M6 は達成後に M7 が機構を置き換えている** — 各項は当時の記録として残す。

1. **M1 コア + CLI 取り込み(らじれこ → NAS)**: `Radirec.Core` にパース→正規化→import-once→
   タグ付与(TagLib#)、`Radirec.Cli` に `radirec ingest --once`。まず `--dry-run`、次に実コピー。
   台帳(SQLite)で冪等。UNC 書き込み。**中心価値**。
   → 計画時の `--once` は**実装されなかった**(#113)。M1 が出したのは `radirec ingest`(常に単発)。
2. **M2 Jellyfin リフレッシュ + 疎通**: `HttpClient` でスキャン起動、スマホ配信まで確認。
3. **M3 常駐化(Windows サービス)**(達成 → M7 で置換): `radirec.exe service`(常駐 verb)で I: を
   常時監視・検知即取り込み。run-as(自分のアカウント)/UNC を整備。ログ整備。当時の**本番の実行形態**。
4. **M4 radikool 移行 + 一括正規化 CLI**: radikool importer + `radirec migrate`。
   `apply-alias` / 一括タグ編集・リネームの CLI。
5. **(保留)M5 デスクトップ編集アプリ**: CLI 運用で不足が出たら着手。要否は運用後に判断(§10.1)。
   受け手トレイ(M6)が同プロジェクト `Radirec.Gui` の最初のスライスで、編集グリッド本体はなお保留。
6. **M6 通知・制御チャネル**(達成 → 機構は M7 で作り直し): 取込結果のデスクトップ通知(§7.1)と、
   利用者→常駐の制御チャネル(§7.2)。取込要約シグナル発行(EventLog)+ 受け手トレイ `Radirec.Gui`、
   named pipe の `status`/`rescan`/`reload`([ADR-0008/0009/0010])。受け手トレイは M5 の tracer slice を兼ねる。
7. **M7 トレイ常駐 per-user 移行**(出荷済み・エピック #62、2026-07-19 完了): 本番の常駐を
   Windows サービスからトレイ常駐へ移す([ADR-0012](adr/0012-retire-service-for-tray-resident-per-user.md))。
   ワーカーを `Radirec.Gui` へ畳み、EventLog シグナル・named pipe・資格情報ダンスという **Session 0 橋を撤去**。
   通知・制御・履歴はすべて in-process。非 admin の per-user install と Velopack 自己更新を解錠
   ([ADR-0013](adr/0013-velopack-per-user-updates.md))。**M3 / M6 の機構はここで置き換わった**
   (ユーザー体験と、通知・制御のドメイン概念は不変)。
8. **M8 管理画面**(設計確定 2026-09-25。エピック #159): 番組の設定の編集・要対応・取込履歴・
   バージョン情報を 1 つのウィンドウに集め、トレイのメニューと通知を絞る(§10.3、[ADR-0017](adr/0017-management-window-owns-programs-json.md) /
   [ADR-0018](adr/0018-attention-items-derived-from-state.md))。M5 の編集本体ではなく、§10.1 のゲートは残る。

## 14. 配布・ブランディング(将来の派生)

- **位置づけ**: 「**らじれこを補完する / 痒いところに手が届く**」ツール。配布は**将来の派生**であり、
  まず自分用を仕上げる。現段階では**抽出できる境界を保つ**ことだけ担保する(§10.2)。
- **対象ユーザー**: 非技術者を含むらじれこユーザー。→ 配布形態は **Windows 単体 exe / GUI**。
  よって GUI は個人運用では後回しだが、**配布時の主フロントエンド**になる(整理コアを包む形で設計)。
- **配布範囲**: **整理コアのみ**(らじれこ M4A の rename + タグ正規化)。Jellyfin/NAS 同期・radikool
  移行は同梱しない(個人拡張、§10.2)。
- **抽出を可能にする規律**(今から守る):
  - 個人固有値(I:/Z:/NAS IP/局マスタ)は config のみ。コードにハードコードしない。
  - importer / 出力ターゲットは差し替え式(汎用 = らじれこ importer + `LocalFolderTarget`)。
- **配布着手時に整備**: プロダクト名(現リポジトリ名 `radirec-tool` は内部名)、README/使い方、
  ライセンス、個人データを含まない出荷 config、**らじれこの利用規約・再配布/連携の可否確認**。
- **実装技術**: 配布(非技術者向け exe/GUI)を見据えた技術選定を §11 で扱う(要検討事項)。
