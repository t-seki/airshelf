# 取込失敗は別 EventID の独立シグナルにする(1 アラート種別 = 1 シグナル)

Status: accepted(軸A A3 / #5 配下。requirements §7.1 / [CONTEXT.md](../../CONTEXT.md) の「取込失敗シグナル」)

[ADR-0008](0008-ingest-notification-via-eventlog-signal.md) でサービスは取込**要約**シグナル(成功)を EventLog(EventID 1001)へ発行するようにした。しかし**ファイル単位の失敗**(`IngestOutcome.Failed` = パース失敗・書込/タグ/台帳失敗)は `IngestReport` に入るだけで自由文ログ止まりで、トレイに届かない。A3 はこの失敗をユーザーセッションのトーストへ**能動通知**する。

失敗をどう運ぶかは 2 択で、契約(発行側と受け手の跨プロセス JSON)の同一性を決めるため**ひっくり返しにくい**:既存 1001 のペイロードを拡張するか、別 EventID の独立シグナルにするか。

## 決定

- **失敗は別 EventID `1002` の独立シグナル(取込失敗シグナル)にする**。1001(成功要約)は**拡張しない**。原則として **1 アラート種別 = 1 シグナル**とし、1000 番台の予約枠(ADR-0008)にアラート種別ごとに割り当てる。これにより:
  - **1001 のトリガは不変**(「新規取込が発生したとき」を維持。成功ゼロの全失敗走査で 1001 を出す必要が生じない)。
  - 失敗ペイロードは成功のアルバム木と**別形**を独立に持てる(異質なものを 1 つの envelope に同居させない)。
  - 将来の**反映失敗**(Jellyfin 更新の失敗 = `RefreshError`。取込は成功しているので別物)も、さらに別シグナル(例 `1003`)として同じ原則で足せる。
- **ペイロードは 1001 と同じ流儀**(count + 上限付きリスト + `truncated`)。`schemaVersion` は 1002 独自の版線として **1 から**始める(1001 とは独立に進化)。`files[]` は `{ name(ファイル名のみ), reason(失敗理由) }`。CJK を膨らませない `UnsafeRelaxedJsonEscaping`。フルパスは晒さずファイル名のみ。
- **発行側で de-dup する(失敗の重複排除)**。`Failed` は台帳(import-once)に記録されないため periodic スキャン(安全網)で毎回再列挙・再失敗する。素朴に「失敗があれば発行」だと**壊れた放置ファイルが走査ごとにトースト**を出す。そこで失敗を**永続ストア**に記録し、**新しく現れた失敗だけ 1002 を発行**する:
  - 鍵 = **ソースパス + フィンガープリント(mtime + size)**。同じパスで別物に差し替わったら再通知する。
  - **成功したらエントリを消す**(一時失敗=ディスク満杯等は次走査で成功して自動クリア。将来また失敗したら再通知)。
  - **サービス再起動を跨いで永続**(さもないと再起動ごとに standing な失敗を全部再通知する。[A2](../../CONTEXT.md) の RecordId baseline リセットと同種の轍)。
- **受け手は A2 の 2 フェーズ機構を同一 subscriber で再利用**する。EventLog query を `EventID=1001 or 1002` に広げ、**チェックポイント(RecordId)はログ位置なので EventID 非依存で 1 個**が両シグナルを覆う。drain / live は EventID で成功/失敗へ振り分け、不在中サマリは成功・失敗で**別トースト**(別シグナルゆえ別通知)。失敗は Warning アイコンで成功と区別。
- **失敗も不在中サマリ(catch-up)に参加させる**。**de-dup があるからこそ必須**:一度発行した 1002 は再発行されないため、トレイ不在中のライブ 1002 を catch-up しないと**その失敗を永久に見逃す**(de-dup + 非 catch-up = 失敗が無言で消える)。
- **2 ツリー疎結合は不変**。繋ぐのは EventLog 上のバージョン付き JSON 契約だけで、`Radirec.Gui.Core` は失敗 DTO を**自前保持**(型共有せず)。ドリフトは golden JSON + 実サーバ往復の契約テストで検出する(1001 と同じ流儀)。

## なぜ別 EventID か(1001 拡張ではなく)

- **概念の清潔さ**: 失敗は成功要約とは別種のシグナル。CONTEXT.md の「取込要約シグナル」(成功限定)の定義を書き換えずに済む。
- **トリガ不変**: 1001 を拡張すると「成功 or 失敗で発火」へ意味が漂流し、全失敗走査でも 1001 を出す羽目になる。別 ID なら 1001 は手つかず。
- **前方互換**: 「1 アラート種別 = 1 シグナル」は将来のアラート(反映失敗等)を envelope 肥大なしに足せる原則を確立する。ユーザーも「反映失敗は別物として後々」と明示的に支持。
- **コスト**: 受け手が複数 EventID を扱う必要が出るが、チェックポイントは 1 個で済み(ログ位置は ID 非依存)、A2 の 2 フェーズ機構をそのまま再利用できる。

## Considered Options

- **(採用) 別 EventID 1002 + 発行側 de-dup + catch-up 参加** — 概念清潔・1001 不変・前方互換。受け手の複数 ID 対応と失敗ストアが要る。
- **1001 ペイロード拡張(schemaVersion 1→2)** — catch-up 再利用は自動だが、1001 のトリガ意味論が漂流し、成功木に失敗を同居させ、glossary を書き換える。契約の同一性を汚す。
- **de-dup せず毎走査発行** — 追加状態ゼロだが、台帳に載らない `Failed` が periodic 毎に再失敗しトースト連発。homelab の放置ファイルで確実に苦痛。
- **失敗はライブのみ(catch-up 非参加)** — 受け手が単純だが、de-dup と組み合わさると不在中の失敗を永久に見逃す。

## Consequences

- **新規の永続失敗ストア**が要る。Windows の SQLite ファイルロックを増やさないため、既存台帳(SQLite)に失敗テーブルを足すのが自然(別ファイルにしない)。
- **受け手 subscriber が複数 EventID 化**する(A2 実装の拡張)。drain / live / 不在中サマリが EventID で分岐。チェックポイントは共有 1 個。
- **要実機検証(Windows)**: EventLog 経路は WSL で実行不可。失敗の発行 → 1002 → トレイ(ライブ/不在中サマリ)、de-dup(同じ失敗が再通知されない・成功で解除・再起動を跨いで抑制継続)を母艦で確認する。純粋ロジック(de-dup 判定・失敗マージ・整形)は WSL 単体テスト。
- **配布は publisher とセット**(契約変更)。publisher(Hosting: 1002 発行 + 失敗ストア)→ receiver(Gui: 1002 対応 + catch-up 拡張)の 2 PR に分け、golden JSON で契約を固定してから受け手を追従させる。
- **反映失敗(RefreshError)は本 ADR の対象外**。将来さらに別シグナルとして同じ原則で扱う。
- **失敗ストアに reaper は置かない**。エントリは成功取込でのみ消える(suppress-until-success)。失敗した
  まま削除・移動されて二度と取り込まれないファイルの行は残り続けるが、homelab 規模では成長は緩慢で無害。
  必要になったら走査時に現存パス集合との差分で掃除する reaper を後付けする(現時点では過剰)。
