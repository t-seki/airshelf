# 出力先の同名衝突は音声部分で同じ内容かを判定し、同じなら取込済みにする

Status: accepted(#79。[ADR-0014](0014-content-fingerprint-import-dedup.md) の残作業。[ADR-0002](0002-same-day-tiebreak-by-time.md) と関連)

[ADR-0014](0014-content-fingerprint-import-dedup.md) で取込の重複判定に内容ゲート(サイズ + 最終更新 + 放送日時)を足し、ソースの番組フォルダのリネームでは再取込されなくなった。残っていたのは出力側の衝突フォールバックである。`LocalFolderTarget` は出力先に同名ファイルがあると、**中身を確かめずに** ` HHmm`(時刻が無ければ ` 2`)を付けて書いていた。ここに来るのは次の 2 つ:

- **正当なケース**:同日・別時刻の別放送([ADR-0002](0002-same-day-tiebreak-by-time.md))。` HHmm` で両方残すのが正しい。
- **重複になるケース**:台帳を失ったとき(内容ゲートも台帳にあるので効かない)、または size/mtime が変わったコピー。同じ内容の near-dup(`… 2024-12-23-1 0830.m4a`)を黙って作る。

出力ファイルはタグを書き換えているので、ソースとのバイト比較やサイズ比較では「同じ内容か」を判定できない。出力タグに放送時刻も残らない。

## 決定

- **同じ内容かどうかは、タグ以外の音声部分で比べる**。TagLib の `File.InvariantStartPosition` / `InvariantEndPosition`(タグ編集で変わらない区間)をソースと既存の出力ファイルの両方で読み、その区間のバイト列が一致すれば「同じ内容」とみなす(`TagLibAudioContentComparer`)。
  - MP4(らじれこ)では `mdat` ボックス、MP3(radikool)では ID3v2 と末尾タグ(ID3v1 / APE)の間になる。`TagLibTagWriter` でタグを書き換えた前後でこの区間が一致することを、両形式のフィクスチャで確かめた(`TagLibAudioContentComparerTests`)。区間の開始位置はファイルごとに読むので、タグが大きくなって音声区間の位置がずれても比べられる(MP3 フィクスチャでは開始位置が 199 → 1347 にずれて一致した)。MP4 フィクスチャは `mdat` が `moov` より前にある構成で位置はずれない。`moov` が前にある実ファイルで位置がずれる構成は、フィクスチャでは確かめていない。
  - **MP4 は `mdat` が 1 つのファイルだけを比較対象にする**。TagLibSharp(2.3.0)の MP4 パーサは `mdat` を見つけるたびに区間を上書きするので、不変区間は**最後の `mdat` しか指さない**。`mdat` が複数ある構成や fragmented MP4(`moof` + `mdat` の繰り返し)では、最後の断片(番組末尾の無音など)が一致しただけで別放送を同じ内容と判定し、書かずに台帳へ記録してしまう(以後の走査でもスキップされ続ける恒久的な欠落)。そこでトップレベルのボックスを先頭から辿り(size/type ヘッダだけ読む。64bit largesize と「size 0 = ファイル末尾まで」に対応)、`mdat` が 2 つ以上ある・`moof` がある・ヘッダが壊れている場合は**判定できない = 違う内容**として扱う。
  - 比較はファイル全体を読むので重いが、呼ぶのは**同名衝突が起きたときだけ**にする。衝突は内容ゲートを通り抜けた後にしか起きず稀なので、そのコストは許容する。**毎回の走査で全ファイルを読むことはしない**([ADR-0014](0014-content-fingerprint-import-dedup.md) の size + mtime ゲートは変えない)。
- **同じ内容なら**:書き込まずに**取込済み**(`済` / `SkippedAlreadyImported`)とし、台帳に記録する。出力パスは既存ファイル。台帳を失った後の再走査で、台帳が自己修復する。
- **違う内容なら**:従来どおり ` HHmm`(時刻が無ければ ` 2`)を付けて書く(欠落させない)。そのうえで結果に警告を残し、常駐は `gui.log` に **Warning** で書く(CLI は出力パスの横に表示する)。同日・別時刻の正当なケースでも毎回起きるので、トーストにはしない。
- **比較の対象**は、ベース名のファイルに加えて、その回が使うはずの ` HHmm` / ` 2` 付きの名前も含める。以前の実装が near-dup を作っていた場合に 3 つ目を作らない。
- **判定に失敗したら「違う内容」として扱う**(読めない・TagLib が解釈できない・不変区間が取れない)。欠落 > 重複(ADR-0014 と同じ非対称リスクの考え方)。比較は例外を投げず false を返す契約にする。
- **dry-run でも同じ判定をする**。同じ内容なら `済` と表示し、台帳には書かない。
- 判定の結果は `IOutputTarget.Plan` が返す `OutputPlan`(書き込み先 / 同じ内容が既にある / 避けた既存ファイル)で運び、取込は `Plan` → `WriteAsync(plan)` の順に呼ぶ。dry-run と書き込みで同じ判定を 1 回だけ行うためである。

## 結果

- 台帳を失った後の再走査や size/mtime の変わったコピーでも、出力先に同じ内容があれば near-dup を作らず、台帳も埋まる。
- 同日・別時刻の別放送は従来どおり両方残り、別名にしたことがログで追える。
- 台帳スキーマは変えない。既存の near-dup ファイルの掃除はしない。
- **残る制限(受容)**:ベース名と ` HHmm` 付きの名前の両方に**別の内容**のファイルが既にある(3 つ目の別放送が同じ名前に来る)と、従来どおりリネームで失敗し、その回は取込失敗として報告される。取りこぼしは失敗通知で見えるので、ここでは扱わない。
