# 時刻なしソースの同日判別はパート序数で行う(dedup のワイルドカードを撤去)

Status: accepted(M4 / radikool 取込。ADR-0002 の「時刻なしワイルドカード」を **supersede**。issue #11 を解消)

radikool(MP3)を取り込むと、放送時刻を持たない録音が台帳に入る。ADR-0002 は「時刻なし = 同日どの
時刻とも一致するワイルドカード」で cross-source 重複排除を意図したが、この規則には 2 つの欠陥がある:

1. **同日重複の取りこぼし(#11)**: あるキーに時刻なしレコードが 1 件でもあると、そのキーのどの時刻の
   照会もワイルドカード一致してしまう。実データの `日向坂46のオールナイトニッポン0(ZERO) 2020-02-23` は
   **中身の違う 2 録音**(51分版とファイル名 `(2)` の 39分版)が時刻なしで同日に存在し、2 件目が「取込済み」
   として静かに欠落する。ADR-0002 が時刻ありソースで解消したはずの欠落が、時刻なし経路で再発する。
2. **PK 衝突**: 現行 PK `(identity_key, broadcast_time)` では、上記 2 録音は両方 `broadcast_time=''` で
   **同一 PK** になり、2 件目の INSERT が落ちる。

よって、同一 `(局,番組,放送日)` の別放送を区別する判別子として、時刻に加えて **パート序数 (part_index)** を
台帳の一意性に含める。時刻なしソース(radikool)はファイル名の重複マーカー `(N)` を part_index に採り、
時刻ありソース(らじれこ)は従来どおり放送時刻 + 統合フォルダ由来の part_index で区別する。
**そのうえで、ADR-0002 の時刻ワイルドカードを撤去し、dedup は `(identity_key, broadcast_time, part_index)` の
厳密一致に統一する。**

## Considered Options

- **(採用) dedup = `(identity_key, broadcast_time, part_index)` 厳密一致。ワイルドカードなし** —
  同日の別放送は時刻 or part_index が異なれば別行として両方取り込む。radikool の `(N)` 付き重複回も欠落しない。
  同一ファイルの再取込は `source_path` 一意(`ContainsSource`)で従来どおり冪等スキップ。
- **ワイルドカードを「そのキーに時刻ありレコードが無い場合のみ有効」に条件化**(#11 の当初案) — 多パート番組の
  欠落は防げるが、radikool 内の同日重複(両方時刻なし)の PK 衝突は解けない。part_index が結局必要。
- **時刻なしに合成時刻(00:00, 00:01…)を振る** — PK 衝突は避けられるが、時刻という属性に嘘の値が入り、
  出力タグや将来の時刻ベース処理を汚す(不採用)。

## なぜワイルドカード撤去が安全か(重要)

ワイルドカードの本来の目的は「同一回を らじれこ(時刻あり)と radikool(時刻なし)の両方で録っていたら 1 回だけ
取り込む」cross-source 重複排除だった。撤去するとこの cross-source dedup は失われるが、**実データ上この衝突は
起こり得ない**: radikool は **2020 年で凍結した過去アーカイブ**(録音アプリ自体が役目を終えている)、らじれこは
**現行放送のみ**を録る。両者は放送日が重ならないため、同一 `(局,番組,放送日)` が両ソースに同時に存在することが
ない。したがって時刻なしと時刻ありが同日で dedup を要する場面が構造的に発生しない。

**トリップワイヤ(将来の保守者へ)**: もし将来「時刻を持たず、かつ時刻ありソースと放送日が重なりうる」新ソースを
追加するなら、この厳密一致 dedup は同一回を **二重取り込み**する。そのときはこの決定を再考し、ソース種別を
台帳に持たせる等で cross-source 同一性を復活させること。撤去した #11 のワイルドカードを安易に戻さない
(粗さが再発する)。

## Consequences

- **part_index の由来**: radikool はファイル名 `(N)` 序数(マーカー無し = 0/単一)。らじれこは統合フォルダの
  並び順(ADR-0002 の既存機構)。いずれも「同日同キーの別放送」を決定的に区別する。序数は連続でなくてよく、
  異なりさえすればよい(例: bare=0 と `(2)`=2)。
- **出力・整列**: part がある回は `… YYYY-MM-DD-N.ext` / `track = MMDD*10+N` / `title (N)`(既存 TagMapper 機構)。
- **台帳スキーマ変更(順序付き冪等マイグレーション)**: `imports` に `part_index INTEGER NOT NULL DEFAULT 0` を
  追加し、PK を `(identity_key, broadcast_time, part_index)` に拡張する。ALTER で PK は変えられないため、
  起動時に **順序付きステップ**で移送する: ① `broadcast_time` 列が無い旧DB → 全面作り直し(両列を得る)
  ② `part_index` 列が無い(= 本番の現行スキーマ)→ rename→create→`INSERT … SELECT`(part_index=0 で埋める)
  →drop で保持移送 ③ 両列あり → no-op。既存行は `part_index=0`。再取込時の冪等性は `source_path` 一意で担保
  されるため(`ContainsSource` が同一ファイルを先に短絡)、既存行の part_index を再導出できなくても二重取込
  しない。
- **デプロイ結合**: 新バイナリを配ると、稼働中サービスが次回起動時に `C:\radirec\ledger.db` を新スキーマへ
  移送する。よって Slice A の出荷は CLI 実行だけでなく**サービス再デプロイ**と結合する(台帳を分けて回避しない
  — サービスが同じ台帳を新コードで開く以上、移送は不可避で、既存のデータ保持パターンで安全に処理できる)。
