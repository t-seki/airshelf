# CLI を普段の運用とエージェントの窓口にし、書き込む操作は制御チャネルで常駐に頼む

Status: accepted(2026-09-25 の grill。[ADR-0012](0012-retire-service-for-tray-resident-per-user.md) の「CLI は dev/batch 専用・named pipe は退役」を改める。[ADR-0010](0010-gui-service-control-via-named-pipe.md) の named pipe を形を変えて戻す。[ADR-0016](0016-reapply-program-settings-to-ingested-episodes.md) の再適用、[ADR-0017](0017-management-window-owns-programs-json.md) の programs.json の書き手と関連)。**#178(2026-09-25)で、取込結果に兄弟フォルダの知らせを含める決定は実装しないことに — 下の注記を参照**。**#179(2026-09-26)で、パイプの名前と同じユーザーへの絞り方を変更 — 下の注記を参照**。**#214(2026-09-27)で、Windows の同じユーザーへの絞り方を再び変更 — 下の注記を参照**

> **#214 で改めた(2026-09-27)**:#179 の「同じユーザーへの制限は `PipeOptions.CurrentUserOnly` で行う」を、Windows ではやめた。
> .NET の `CurrentUserOnly` は、ユーザーの SID ではなく**トークンの所有者**で ACL を作り、相手のパイプの所有者と比べる
> (dotnet/runtime の `NamedPipeServerStream.Windows.cs` / `NamedPipeClientStream.Windows.cs` の `ValidateRemotePipeUser`)。
> UAC で昇格したトークンの所有者は `BUILTIN\Administrators` なので、管理者の端末の CLI が非昇格のトレイに繋がらず、
> 「常駐が動いていません」と誤って答えていた。
> - Windows では `ControlPipeSecurity` が、昇格の有無に関係なく**許可も所有者もユーザーの SID** で作る。CLI は繋いだ後に、
>   パイプの所有者がユーザーの SID かを確かめる(同じ名前で待ち受けるなりすましを拒む。`CurrentUserOnly` の役目を保つ)。
>   昇格した CLI → 非昇格のトレイ、非昇格の CLI → 昇格したトレイのどちらも繋がる。別のユーザーからは今までどおり繋がらない。
> - Windows 以外(CI の Linux)は `CurrentUserOnly` のまま(相手の uid で比べ、昇格の問題は無い)。往復のテストは今までどおり CI で回る。

> **#179 で改めた(2026-09-26)**:決定の「制御チャネルは named pipe を戻す(ADR-0010 の形。同じユーザーだけに `PipeSecurity` で絞る)」のうち、
> 次の 2 点を変えた。
> - **パイプの名前はユーザーごと**(`radirec-control-<ユーザーの SID>`。SID が取れない環境ではユーザー名)。ADR-0010 の固定名
>   `radirec-control` のままだと、同じ PC で 2 人がそれぞれトレイを起動したときにぶつかる。
> - **同じユーザーへの制限は `PipeOptions.CurrentUserOnly` で行う**(`PipeSecurity` より簡単で、Linux でも効くので往復のテストを CI で回せる)。
>
> 受け口・メッセージの型・CLI 側の接続は `Radirec.Hosting/Control/`(`ControlPipeServer` / `ControlPipeClient` / `ControlProtocol`)に置いた。

> **#178 で改めた(2026-09-25)**:決定の「取込結果には統合設定の無い兄弟フォルダの知らせも含める」は実装しない。
> #174(#155・[ADR-0018](0018-attention-items-derived-from-state.md))で取り込みの走査から兄弟フォルダの検出そのものが外れ、
> 取込結果に載せるものが無くなったため。兄弟フォルダは `reapply` の `unintegratedSiblings` と、要対応(管理画面のホームと、#183 で足す CLI の `attention`)で見る。
> grill の会話では「#155 で検出しないと決まれば外す」と話していたが、この ADR の本文には書いていなかった。

ADR-0012 で `radirec.exe` は「dev/batch の単発 CLI で、制御コマンドの移設先ではない」とし、named pipe の制御チャネルも退役させた。
その結果、CLI はトレイの常駐と並んで動くことを考えておらず(常駐中に `ingest` / `reapply` を叩くと、台帳と出力先を常駐の直列ループの
外から書き換える)、状態を見る手段も無い。**普段の運用で、AI エージェントがターミナルやスクリプトから CLI を使えるようにする**ため、
CLI の位置づけを改める。

## 決定

- **台帳を書き換える操作(`ingest`・`reapply`)は、CLI が自分で実行せず、制御チャネルで常駐に頼む**。常駐は再適用のジョブと同じく
  直列ループの上で実行し、結果を CLI に返す。台帳の書き手は常に常駐だけ、という形を保つ。
  - 制御チャネルは named pipe を戻す(ADR-0010 の形。同じユーザーだけに `PipeSecurity` で絞る)。受け口はトレイのプロセスに置き、
    中身は今の `IServiceControl` をパイプの向こうに出したもの。
  - 最初のやりとりで**プロトコルの版**を交換し、合わなければ CLI は失敗する(アプリの版ではなくプロトコルの番号で比べる)。
- **常駐が動いていなければ、頼む操作は決まった終了コード(2)で失敗する**。CLI が自分で実行する代わりはせず、トレイを自動で起動もしない。
  トレイが起動していても取り込みが止まっている(縮退。W-104 / W-105)ときも同じで、理由を添える。
- **`ingest` は「走査を頼み、終わるまで待って結果を返す」**(トレイの手動再スキャンは受理で返るが、CLI は結果が要る)。
  CLI から頼んだ走査は**新規取込のトーストを出さない**(結果は CLI の出力に返る)。
  **取込失敗のトーストは出し、失敗のストアにも記録する**(要対応に載る)。止めるのは成功要約だけ、という #152 / ADR-0019 と同じ形にする。
  記録して通知しないと、失敗のストアの重複抑制で、後の常駐の走査でもその失敗のトーストが出なくなる(ADR-0011 のサイレント抑制)。取込結果には統合設定の無い兄弟フォルダの知らせも含める。
- **`reapply` は、既定で dry-run だけを行い、実行は `--apply <予定 ID>` でだけ行う**。予定 ID は予定の中身から計算するハッシュで、
  常駐は設定リロード → dry-run し直し → ID が一致したときだけ実行する(違えば終了コード 3)。常駐に「直前の確認」を覚えさせないので、
  管理画面の確認と CLI の確認が互いを上書きしない。
- **`status`(状態取得)と `reload`(設定リロード)も制御チャネルで常駐に頼む**。どちらも常駐の中にしか無いもの(ライブ状態・
  常駐が使っている設定)を扱うので、台帳を書き換えなくても常駐を経る。`reapply` の dry-run も、常駐の設定で確かめるので常駐を経る。
- **常駐の中のものを要らない操作は、常駐を経ずに CLI が直接行う**:`ingest --dry-run`(台帳は読み取り専用)、`refresh`、`history`(取込履歴)、
  `attention`(要対応。計算の本体は #155 / #156 / #172)。
- **一回きりの移行のための機能と、設定ファイルの指定を削る**:`ingest --root`(radikool の一括移行。M4-A / #15)、`organize-source`
  (散在ソースの仕分け。#81)、`--config`。CLI は常にトレイと同じ既定の `radirec.json` を使う。これで、制御チャネルに「別のルートで
  走査するジョブ」を足す必要も、CLI と常駐で設定ファイルが食い違う場合の決まりも要らなくなる。
- **`status` は常駐が動いていなくても答えとして返す**(`running: false` と理由。終了コード 0)。
- **すべてのコマンドに `--json` を付ける**。最上位に `schemaVersion` を置き、形を変えるときは番号を上げる。
- **終了コード**:0 = 成功、1 = 使い方の誤り・設定を読めない・版の不一致、2 = 常駐が動いていない、3 = 予定が変わった、
  4 = 完了したが一部の回が失敗した、5 = 外部との接続に失敗した(Jellyfin・NAS)。一部が失敗したときに 0 を返していた今の `ingest` は 4 を返すように変わる。
- **CLI で `programs.json` を編集するコマンドは作らない**。エージェントは `programs.json` を直接編集してから `reapply` の dry-run を叩く。
  これを正式な使い方として認める(ADR-0017 の「エディタで直すのは逃げ道」を改める)。管理画面は、読み込んだときと書く直前で中身が違えば
  書かずに知らせる(`ProgramsFileWriter`)ので、直接の編集を管理画面が黙って上書きすることはない。
- **更新の確認・適用と、縮退中のトレイの再起動は CLI に載せない**(トレイと管理画面の役目のまま)。

## 検討した案

- **CLI が自分で実行し、台帳・出力先のロックで常駐と排他する**:常駐の直列ループが守っている不変条件(取り込みと再適用が同時に走らない、
  リロードと再適用の間に取り込みを挟まない)を、ロックで作り直すことになる。状態の表示と再スキャンは結局プロセス間の経路が要る。採らない。
- **常駐が動いている間は、CLI の書き込む操作を拒否する**:「普段の運用で使う」という目的と両立しない。採らない。
- **常駐が動いていなければ CLI が自分で実行する(今の動き)**:途中でトレイが起動すると、起動時のキャッチアップ走査と並んで走る。
  防ぐにはロックが要り、上の案と同じ問題になる。採らない。
- **常駐が動いていなければ CLI がトレイを起動してから頼む**:CLI を叩くだけで常駐という長く続く副作用が起き、デスクトップのセッションの
  外から叩いたときの挙動も読みにくい。採らない。
- **`reapply` の実行に予定 ID を求めない(今のまま)/ 任意にする**:エージェントが見ていない予定で実行されうる。採らない。

## 結果

- CLI の `reapply` は、オプションなしで実行しなくなる(仕様の変更)。`ingest` の終了コードも変わる。
- トレイのプロセスに named pipe の受け口が戻る。`IServiceControl` に「走査して結果を待つ(新規取込のトーストなし。失敗のトーストは出す)」と「予定 ID で実行する」が加わる。
- `SourceOrganizer` と取り込みのルートの上書き(`CompositionRoot.Build` の `rootOverride`)は使う所が無くなるので消す。
  もう一度一括移行が要るときは、そのときに作り直す。`--config` の説明のための `ConfigPaths.DefaultConfigDisplay` も使い道が無くなる。
- 開発機で、トレイを動かさずに CLI だけで本番の取り込みを試す手段は無くなる(`ingest` は常駐に頼み、`--config` も無い)。
  CLI だけで試せるのは `ingest --dry-run` まで。README と usage の開発手順(`--config radirec.json`)は既定の場所を使う形に直す。
- 「管理画面の確認と CLI の確認が互いを上書きしない」は、CLI の確認が常駐の「直前の確認」(`_lastReapplyPlan`)に触れない別の経路を
  通るときだけ成り立つ。今の `PlanReapplyAsync()` をそのまま使うと、管理画面で開いている確認が IsStale になる。
- #4(radikool 移行 + 一括正規化 CLI)の残り(`migrate`・`apply-alias`・一括タグ編集)は、この決定と逆向きなので作らない。
- `requirements` §7 の `Radirec.Cli` の説明(dev/batch の単発 CLI)を改める。
